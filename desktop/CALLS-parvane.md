# Parvane — звонки (дизайн, безопасность в основе)

Голосовые/видео-звонки 1-на-1. Два слоя, как в Telegram, но сигналинг — наш
(NATS-шард `call`), медиа — стандартный WebRTC, а **защита от MITM встроена
криптографически через ключи идентичности**, а не только через ручную сверку
эмодзи.

## Слои

1. **Сигналинг** — шард `call` релеит `call.signal` → `call.user.<id>`
   (fire-and-forget). Уже готов и оттестирован. Несёт стандартный WebRTC-обмен:
   `invite`(SDP-offer) / `answer`(SDP-answer) / `ice`(candidate) / `reject` /
   `hangup`. Заменяет весь MTProto `phone.*` Telegram.
2. **Медиа** — обычный `webrtc::PeerConnection` (libwebrtc из
   `ThirdParty/tgcalls`). DTLS-SRTP шифрует поток по умолчанию. НЕ используем
   собственный сигнальный протокол tgcalls — наши SDP/ICE ложатся на голый
   PeerConnection 1-в-1.

## Модель безопасности

**Проблема голого WebRTC:** DTLS-SRTP привязывает ключи медиа к отпечаткам
DTLS-сертификатов, которые едут ВНУТРИ SDP через наш шард. Скомпрометированный
шард может подменить отпечаток → незаметный MITM.

**Наше решение — аутентифицированный сигналинг на ключах идентичности:**

- У каждого пользователя есть **своя пара Ed25519** (приватный ключ живёт на
  устройстве, в `-workdir`; НЕ уходит с машины). Это НЕ серверный ключ identity
  (тем подписываются JWT) — это ключ пользователя.
- Публичный ключ **регистрируется в каталоге identity** (`identity.user.setkey`)
  и раздаётся через `resolve`/`search` (поле `UserInfo.pubkey`).
- Каждый `invite`/`answer` несёт **подпись `sig`** над `call_id || sdp`,
  сделанную приватным ключом отправителя.
- Приёмник берёт `pubkey` отправителя из identity, проверяет `sig`. Не сошлось →
  **звонок отклоняется** (возможный MITM). Шард без приватного ключа подделать
  подпись не может → MITM закрыт **без участия пользователя**.

**Эшелонирование:**
1. Подпись SDP ключом identity — основной рубеж (крипто, автоматом).
2. TLS на NATS — сигналинг (SDP/ICE с IP) не читается на сети. (TODO инфра)
3. SAS/эмодзи-фингерпринт (4 эмодзи из хэша ключа) — рубеж «для людей», на
   случай недоверия каталогу ключей. (TODO, как в Telegram)

**Доверие каталогу ключей:** identity отдаёт `pubkey`. Если не доверять
identity — остаётся SAS-сверка голосом (рубеж 3). TOFU (запоминание ключа при
первом звонке) + предупреждение о смене — тоже возможны позже.

## NAT-траверс

ICE-серверы отдаются в `invite` (поле `ice_servers`). STUN — публичный/свой;
TURN (relay, когда P2P не проходит) — свой `coturn`, аналог relay Telegram.
Только-relay режим прячет IP пиров друг от друга.

## Этапы

- **Э1 (этот заход): раздача ключей + аутентификация сигналинга — БЭКЕНД.**
  identity: колонка `pubkey`, `identity.user.setkey`, `pubkey` в resolve/search.
  parvane-types/-core: `sig` в invite/answer, тесты. Крипто-агностично на
  бэкенде (identity хранит opaque-строку ключа).
- Э2: клиентская генерация/хранение пары + подпись/проверка (Ed25519 в C++).
- Э3: медиа-контроллер `ParvaneCallController` вокруг `webrtc::PeerConnection`,
  связка с `CallClient`; audio-only.
- Э4: UI-врезка (кнопка звонка, панель, стейт-машина из `calls/`).
- Э5: свой `coturn` + ICE-серверы в сигнале.
- Э6: видео + SAS-эмодзи + TLS на NATS.

Аудио-раунд-трип проверяется вдвоём (реальный звук, headless не поймать).
